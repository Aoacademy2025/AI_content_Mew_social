# HERO-58 Task 1 — synthetic upload and full-render profile

Date: 2026-09-29. Branch `codex/hero-58-upload-render-performance`, baseline `3a0e4925a9546b3be81f6544d6d46145d9a301e0`. This is local research, not a shipped speedup. It follows the approved plan and read-only production baseline in the separate coordinator worktree (`docs/plans/2026-09-29-hero-58-upload-render-performance.md` and `docs/audits/2026-09-29-render-latency-baseline.md` there). Tracking: [HERO-58](https://linear.app/mew-social/issue/HERO-58). No customer media, database, provider, production host, or account was used.

## Path exercised and measurement boundaries

1. Editor Post phase sends the file from `BrollWindowInspector.tsx` to `/api/videos/broll-window/upload`. The upload route checks auth, plan, type, byte size, concurrency admission and ffprobe dimensions. It streams the file to disk, then calls `applyKenBurns` for an image or `normalizeForRemotion` for video. Those exact functions in `src/lib/broll-asset-lib.ts` construct and run the production ffmpeg commands. The harness calls them on local synthetic files. It does **not** measure browser transfer, multipart parsing, route auth/admission, or its stream-to-disk time.
2. The editor later submits `mode: broll-rerender` with the returned `/api/stocks/...mp4` source. `src/app/api/videos/jobs/route.ts` validates ownership and `windowEdits`; `src/lib/mcp/orchestrator.ts` revalidates and merges edits against the source preview, clears `keywordPopups`, and calls `/api/videos/render` for the **entire base timeline**. Avatar or uploaded-presenter composite can follow. The harness uses the real `validateWindowEdits`, `mergeWindowEdits`, and `prepareBrollRenderAssets` functions with synthetic URLs and local files, then calls the real `runRender` core. Auth, database writes, job queue, provider calls and avatar composite are outside this fixture.
3. `runRender` bundles `src/remotion/index.tsx`, selects `ShortVideoComposition`, and calls Remotion `renderMedia`. `ShortVideoComposition` renders normalized B-roll via `OffthreadVideo`, full-frame cover, the existing visual grade, crossfades, cinematic overlays, end fade, and the synthetic narration audio. The fixture uses no watermark (paid upload), BGM, avatar or subtitle burn. Empty `keywordPopups` matches the B-roll apply base-render branch. This is the base renderer seam responsible for most of the production cohort's processing time, not an end-to-end customer operation.

The production upload cohort contains 99 completed jobs with at least one uploaded replacement: median post-submit processing 327.766 s, p95 796.723 s, and child rendering 97.95% of aggregate processing. Median media duration is 87.222 s. Those observational values exclude upload time. The two original support operations had five uploaded replacements plus timing edits. The local fixture is a 60 s lower-bound representative timeline; it is not a replay of those jobs.

## Fixture and runtime

Reproducible harness: `scripts/benchmark-hero58-upload-render.ts`. All generated input, output and logs are under ignored `.tmp/hero58/` and must remain uncommitted. `ffmpeg` creates a synthetic 540×960 JPEG, 5 s 540×960 24 fps MP4, 5 s synthetic base MP4 and 60 s sine-wave WAV. The actual upload functions produce a 5 s 1080×1920 30 fps no-B-frame H.264 Ken Burns clip and a 5 s 540×960 30 fps no-B-frame H.264 normalized video (normalization deliberately does not upscale). The renderer outputs 1080×1920 at 30 fps, 1,800 frames, with AAC audio. Fifteen four-second windows fill the timeline. One-window cases replace one window with either uploaded still or video. The final mixed case replaces five windows with **five distinct uploaded asset paths** (two still-derived and three video-derived MP4s); the remaining ten windows reuse a synthetic base clip. The input media patterns repeat across those distinct paths, so visual diversity is less than real uploads.

The harness serves synthetic media on `127.0.0.1` using GET/HEAD, byte ranges, `Cache-Control: public, max-age=86400`, and the same stock-route CORS headers. Production `src/app/api/stocks/[filename]/route.ts` delegates to `src/lib/media-serving.ts` and a storage adapter; localhost's simple filesystem server does not capture Next overhead, remote storage, real network throughput, or its caching behavior. No local SQLite is needed because all auth and persistence boundaries are bypassed; nothing accesses the repo's development or production DB.

Local machine: macOS arm64, Node 26.7.0, 10 reported CPUs and 16 GiB RAM, system ffmpeg 8.1.2, installed Remotion 4.0.509 (lockfile resolution of the `^4.0.427` package declaration). Production baseline was 8 vCPU/32 GB Linux with no GPU, **two PM2 render-worker OS processes** and three frame threads per worker. The local concurrent pair uses `Promise.all(runRender)` in **one Node process**; it shares the bundle cache and render slot registry, unlike production's two workers. The harness pins three frame threads, 128 MiB offthread cache, JPEG quality 90, and two local render slots. Local `os.freemem()` crossed the renderer's 2 GiB threshold: the first unpinned singles selected `lowResource=true` (x264 `faster`), but the first unpinned pair selected `false` (x264 `medium`). That pair cannot be compared causally with the singles. The five-distinct-file comparison therefore pins `RENDER_LOW_RESOURCE=1` for every run. This is a safer local controlled profile, **not guaranteed to match** the production automatic x264 preset and not a production tuning recommendation.

## Results

All times are wall-clock milliseconds except where noted. `prep` is validate, merge, asset resolve and ffprobe coverage preparation. `render slot` is from `onRenderStart` through `runRender` completion, including Remotion frame work and final encode/stitch. `pre-render` is bundle/metadata/slot admission before that callback. Local queue wait was 0 ms for all listed jobs.

| 60 s, one still replacement | see upload above | 56 | 1,151 | 73,578 | 74,729 | Unpinned, `lowResource=true` |

The first upload normalization observations were 559 ms for a 42,609-byte synthetic JPEG to a 1,705,505-byte MP4 and 143 ms for a 2,309,041-byte five-second MP4 to a 2,723,815-byte normalized MP4. The distinct-file run repeated the real functions for one more image (475 ms) and two more videos (137/130 ms). These times exclude transfer and route overhead. Files are tiny/simple relative to the allowed 20/200 MB uploads, so they cannot bound actual customer normalization.

Temporary source-local instrumentation read Remotion's `renderMedia` progress object in `run-render.ts`; the source edit was fully restored before this report. For five distinct uploads, `renderedDoneIn` was 59,556 ms for one job and 97,357/98,101 ms for the pair. `encodedDoneIn` was 7,555 ms and 12,885/12,801 ms, respectively. In installed `node_modules/@remotion/renderer/dist/render-media.js`, `renderedDoneIn` is measured from `renderStart` through completed frame rendering and a possible parallel prestitcher wait (around lines 113–120 and 410–425); `encodedDoneIn` is measured from the later `stitchStart` to final stitch progress (around lines 425–453). They are **different elapsed clocks**. In these local runs the final progress had `stitchStage=encoding` and the two values summed to within about 0.1 s of render-slot wall time, indicating sequential frame/prestitch and final encoding on this machine. In other Remotion modes, earlier encoding may overlap frame generation. Even here, `renderedDoneIn` includes more than pure browser composition or decoding, so these values cannot identify a specific frame-work hotspot.

A single snapshot during the controlled pair showed 14 Chromium processes at approximately 665% aggregate CPU and 3.4 GiB RSS, plus two Remotion compositor processes at approximately 22% CPU and 460 MiB RSS. This supports substantial browser/frame work in this local run, but other host processes were active; one snapshot does not identify a specific Chrome hotspot or establish production CPU contention. The controlled same-process pair's per-job elapsed time was about 1.64–1.65× the single, while two jobs finished in approximately 111 s. It does not predict production's two-process throughput or queue time.

The three controlled five-upload outputs were **byte identical**, SHA-256 `3d927577e7df0f5bfa24a2ce7be9ea1770ad7dd39f3ccd26a1c3420c2b`. ffprobe confirmed H.264 1080×1920/30 fps/1,800 frames and AAC audio, duration 60.053333 s. This checks fixture repeatability across one/two local slots; no production change has been made.

## Diagnostic candidate and ruling

The code provides one bounded, quality-preserving diagnostic lever: `RENDER_OFFTHREAD_CACHE_MB` controls Remotion's decoded-frame cache via `resolveOffthreadCacheBytes` in `src/lib/offthread-cache.ts`. Repeated use of the synthetic base clip could cause cache misses even though compressed source files total less than 128 MiB. A temporary 128→256 MiB single-job ABBA probe on the exact same five-upload inputs held fps, resolution, frame threads, JPEG, x264 preset, timeline and audio fixed. All four outputs had the same SHA-256 as the controlled baseline above. The exact render-slot times were:

| Order | Cache | Render-slot time | Resolved profile |
|---|---:|---:|---|
| A1 | 128 MiB | 68,801 ms | 3 frame threads, lowResource=true |
| B1 | 256 MiB | 68,528 ms | same |
| B2 | 256 MiB | 69,701 ms | same |
| A2 | 128 MiB | 68,416 ms | same |

The 128 MiB mean was 68,609 ms; the 256 MiB mean was 69,115 ms, 506 ms slower. The first adjacent pair favored 256 MiB by 273 ms and the reverse pair favored 128 MiB by 1,285 ms. There is no repeated gain. A 256 MiB setting would reserve up to an extra 128 MiB per active render job (256 MiB for two production workers), and a production config change is outside approved scope. **Ruling: discard this cache increase as a HERO-58 fix.** This does not prove cache behavior for larger or more complex real uploads, which were deliberately not replayed.

No source-specific production correction is yet justified. Upload normalization is measurable but much smaller than the observed local full render for these small inputs, while the production cohort excludes upload time and contains unknown asset sizes. The renderer receives merged media URLs and timing after validation, not an upload-specific compositing mode. Remotion's elapsed milestones show costly frame/prestitch work but do not separate decoding, local media serving, browser layout/filtering, frame capture or parallel encoding. The smallest next discriminating experiment is a local Linux 8-vCPU/32-GB fixture with **the same media/settings**, per-frame time distribution (`renderMedia` frame callbacks), Chromium CPU profile, compositor process CPU, and media GET/range byte counts/cache hits. Only a repeated profile that isolates redundant work and passes pixel/audio output parity should enter Task 2. No config, schema, dependency, concurrency, quality, billing, ownership, validation or single-window splice change is proposed here.
