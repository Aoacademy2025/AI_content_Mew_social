# V6 final pre-flight verdict: NOT READY

1. **The ablation CER gate has no defined controlled scoring batch.** The plan requires all eight ablation WAVs to have raw canonical CER `<=0.10` before any final job may be dispatched, but the actual-runtime protocol freezes an `evaluatorBatchId`, runs the pre/post three-process fixture, and forbids restart/drift only for the later 36-file final batch. The final files do not yet exist when the ablation decision must be made, so the stated final-batch protocol cannot implicitly cover the ablation scores. As written, a payment-controlling ablation decision can be produced without the required actual arm64 fingerprint/fixture guarantees. Define a separate ablation evaluator batch with the same non-emulated arm64 fingerprint and immediate pre/post fixture requirements (and bind every ablation CER record to it), or explicitly define another complete protocol that covers the eight files before final dispatch.

2. **The v2 baseline's claimed outbound proof is not yet bound to the exact bytes sent.** V3 independently recomputes `request_commitment_sha256` and echoes both commitments, but v2 has no echo. For v2, the plan says equality is proved by semantic descriptors and exact wire hashes; two different arm wire hashes cannot prove field equality, and constructing a descriptor beside a request does not prove that the descriptor was derived from the byte buffer actually passed to `fetch`. `pair creation rejects descriptor/hash mismatch` does not define the verification algorithm. Before this can support the fixed condition-matching claim, require the v2 semantic descriptor to be deterministically derived by parsing the committed exact provider request bytes (including an explicit definition of the RunPod outer envelope versus worker `input`), then compare the decoded sensitive-field hashes/settings against the frozen manifest before dispatch and again before pair creation. Otherwise a serialization/mapping defect can send different baseline text/settings while all current commitments still pass.

3. **Accepted jobs with unreadable provider outcomes do not fit the promised exact counter partition, and their terminal-state precedence is ambiguous.** The report counters partition dispatch as `provider_accepted | provider_rejected | transport_unknown`, but the only post-acceptance outcome counters are `valid_completed`, `provider_terminal_failed`, and `application_validation_failed`. A provider-accepted job that ends locally as `failed_poll_unavailable`, `failed_provider_missing`, `failed_cancel_unconfirmed`, or with park unconfirmed has no truthful terminal bucket: its provider outcome is unknown, not `provider_terminal_failed`, and it is not application validation failure. In addition, the matrix first makes poll/status/missing states terminal and then says a failed cancel should use `failed_cancel_unconfirmed`, without defining whether that replaces the prior terminal state or is a separate cancellation disposition. Add an accepted-provider-outcome-unknown counter/disposition and explicit conservation equations, and define non-overwriting precedence or separate orthogonal job/cancel/park fields so every accepted slot appears in exactly one outcome bucket after crashes and reconciliation.

4. **The forced-park schedule contradicts the 660-second cost bound.** The budget contract reserves `540 execution + 60 startup/idle + 60 forced-park grace = 660` seconds, but the failure procedure observes until exactly 660 seconds after pre-dispatch and only then forces `workersMin=0, workersMax=0` and performs readback. That leaves no included forced-park grace; any billing between the t=660 park request and confirmed parked readback exceeds the reserved upper bound. Freeze an authoritative timeline that initiates forced park early enough for the full grace to end by t=660 (or increase the per-slot bound and rerun the `$10` inequality), including queue/cold-start and control-plane/readback time. Until then, the absolute cost acceptance criterion is not enforceable.

5. **The HMAC protecting the counted loopback submit route is not specified by the otherwise exact key contract.** The route requires a “review-key HMAC over run/slot/revision,” but the HKDF contract defines only owner, reveal, and score keys; it does not define whether submit uses raw IKM or a derived key, the exact message bytes/JCS schema, output encoding, or replay/one-use rule. Harness and app can therefore implement incompatible or security-different authenticators while each appears compliant. Define a domain-separated submit key and exact canonical message/serialization and verification rules. Also state the exact byte encoding of the owner-ID HMAC input, because account hard-delete depends on reproducing that value across every run.
