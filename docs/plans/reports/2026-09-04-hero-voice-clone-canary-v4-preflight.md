# NOT READY

1. **The final blind comparison has an arm-revealing signal in the audio itself.** Every `combined-v1` final candidate is AudioSeal-watermarked, while audited-v13 baseline audio is not. A reviewer (or any pre-lock client with the audio token and the pinned detector) can distinguish candidate from baseline before lock by testing `detect_fraction`, even though the plan requires 18 leak-free pairs and says pre-lock audio/API payloads contain no arm or reveal information. The fixed manifest message makes this a deterministic side channel, not merely a metadata risk. The plan must specify a final-comparison treatment that preserves the intended audio pipeline while preventing watermark presence from identifying the arm, and it must test that predicate before review opens.

2. **Account hard-delete does not have the claimed single authoritative terminal mutation.** It must delete the application user and `UserVoice` rows in the application database and matching `ReviewRun` rows in a separate isolated SQLite database. Those mutations cannot be the plan's “single defined database/state mutation,” and reconciliation is told to use both user existence and review-row existence while also claiming “exactly one authority.” A crash after one database commits but before the other commits leaves a state for which “restore files if mutation fails / unlink if it succeeds” has no defined answer; deletion of the user may also be irreversible. Define an explicit durable coordinator/commit order, every partial-commit state, compensation limits, and the one terminal receipt/invariant for each state, then add crash tests at every cross-database boundary.

3. **The application state used by the counted AI Studio runner is not explicitly isolated from production.** The plan isolates the private review store in local SQLite, but `CandidateAiStudioV3` intentionally exercises the normal durable job, attempt, reservation/credit, ownership, and `UserVoice` paths with Mew's authenticated account. No fixed contract binds those application records and reference storage to a named non-production database/tenant, nor explains how Mew ownership is represented there. “Production database unchanged” is only a later readback, not a fail-closed configuration requirement. Require explicit non-production application DB/auth/credit/storage bindings at startup and in the immutable run manifest, reject production identifiers/DSNs, and verify them before the counted smoke.

4. **Run-level behavior after a known final-slot failure is ambiguous, so the 44-versus-abort contract is not executable deterministically.** Unknown-submit and failed ablations explicitly stop later dispatches, but explicit rejection, timeout, identity failure, malformed output, or invalid/missing baseline/candidate audio are only terminal for the slot. Task 7 can be read to continue the remaining slots and report `NO-GO`, while the global rule permits fewer than 44 only for a “declared breaker” without enumerating which final failures are such breakers. Add a run-level transition table for every terminal slot outcome stating `continue` or `abort`, and test the exact dispatch count/restart behavior for each branch.

5. **The frozen final-settings claim is internally inconsistent with the contract-v3 wire schema.** The settings commitment includes `mixedLanguage`, and the plan says the same final settings are sent to both arms, but contract v2 sends `mixed_language:true` while the exact contract-v3 request has no corresponding field. If candidate behavior is intended to be a fixed worker constant, that constant is neither part of the request nor explicitly included in the accepted response identity/settings commitment. Add it to the v3 contract or define and attest the immutable worker constant in the exact v3 success envelope; then make pair creation reject any baseline/candidate disagreement in the full committed settings object.

6. **The remote Git commitment is not specified precisely enough for byte-level verification.** The private ciphertext envelope is byte-exact, but the public commitment is only described as a “small” object containing three fields. Its exact schema, canonicalization/newline rule, repository path, Git object kind (blob/tree/commit), and remote-ref readback procedure are unspecified, while lock/reveal depend on “the recorded Git object ID.” Define the exact committed bytes and path, record the commit ID plus blob ID, require remote readback of that exact path/blob, and state which immutable ID lock/reveal verify. Without this, two implementations can satisfy the prose while verifying different objects.

7. **The US$10 breaker leaves `staging_infrastructure_charge` and post-unknown observation cost unbounded.** The formula names those values but does not define their included billable resources, measurement interval, rounding unit, or a conservative time cap from endpoint provisioning through drain/parking. On unknown submit, the endpoint may remain under observation until an unspecified deadline, yet the ledger commits only 600 seconds for the slot. Predeclare the observation deadline, include every endpoint/worker/build/storage charge through forced parking in the integer-micros reserve, and fail preflight if any component lacks an authoritative worst-case bound.
