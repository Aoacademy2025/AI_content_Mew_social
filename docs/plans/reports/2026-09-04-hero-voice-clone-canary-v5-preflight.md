# NOT READY

1. **The run-level CER rule contradicts the ablation gate and is not exact by phase.** The failure table says any valid WAV with CER `>0.10` continues because the candidate gate permits one, while the fixed ablation contract and Task 7 require every ablation output to have CER `<=0.10` and abort before finals on failure. The same row also fails to distinguish final-baseline CER (no threshold is declared) from final-candidate CER (at most one failure is permitted, with the complete 18-candidate denominator retained). Replace the generic CER row with separate ablation, final-baseline, and final-candidate rows, each fixing run state, later-dispatch behavior, and when `completed_no_go` is chosen.

2. **The “identical final text/full echoed settings” acceptance claim cannot be proved by the declared v2 runner and is underspecified for v3.** `BaselineV13Direct` accepts a v2 response using worker/catalog identity, similarity, and WAV validation; the declared audited-v13 response does not echo `text`, `speed`, `num_step`, or `mixed_language`. The v3 success contract explicitly echoes only `mixed_language:true`, yet Task 5 and Acceptance Criteria require both arms to echo identical final bytes/full settings. Do not require an impossible v2 echo. Define one exact proof contract: freeze and hash the exact outbound v2/v3 request bytes before dispatch, validate all fields available in each immutable response schema, require the v3 envelope to echo a canonical request/settings hash if supported, and state that v2 equality is proved from the fsynced outbound request snapshot rather than a nonexistent response echo. Also define whether the “full settings” hash is deliberately limited to `{speed,numStep,mixedLanguage,outputRate,outputChannels,outputSubtype}` and keep arm-specific seed/profile/guidance/ranking outside that matched-settings claim.

3. **Unknown-submit accounting cannot satisfy the requested “exact submitted/completed/failed counts” as written.** A crash after the fsynced `submitting` record but before or during the network call, or a transport-unknown response, cannot establish whether RunPod received the job. Elsewhere the plan derives attempts from pre-dispatch records and calls every such record a `/run` dispatch attempt, which overstates what is known. Define disjoint report counters and ledger states for `dispatch_intent`, `confirmed_request_sent`, `provider_accepted`, `provider_rejected`, `transport_unknown`, `completed`, and terminal failures. A completed run may still require 44 confirmed sent/accepted slots with 44 valid terminal outputs; an aborted unknown-submit run must report the submitted count as a bounded/unknown value, not an exact number, while still charging the full 660-second reserve and counting the slot once against the 44-slot ceiling. State explicitly that the counted smoke is identified by its immutable slot ID and can appear in only one of those categories.

4. **The exact run-level failure table omits failures after a known `/run` acceptance.** There is no row for repeated poll transport failure, malformed poll response, provider `/status` `404`/job disappearance, inability to cancel a known job, or inability to drain/park after a known job. The plan mentions `/status` `404` only as non-evidence of deletion, so implementation cannot derive the required job/attempt state, application-credit settlement, external-cost commitment, observation deadline, or later-dispatch rule. Add explicit rows for each condition. They must fail the run closed, prohibit later dispatch, retain a conservative external reserve until the bounded observation/park rule completes, and specify the exact terminal durable/client states without implying provider erasure.

5. **The supposedly exact JCS/AES-GCM commitment is still implementation-dependent, and the expected remote repository is not pinned.** Fix the HKDF hash, salt/extract rule, and byte-exact `info` labels; AES-GCM tag length; whether `ciphertext` excludes the separately stored tag; and the encoding of `aadSha256` (for example, 64-character lowercase hex). For the remote check, freeze the canonical repository identity/URL (or immutable host repository ID), remote ref, and commitment path before review; verify that the expected remote advertises the pushed commit; then record that repository identity together with commit SHA, object-format-qualified blob OID, path, and blob-byte SHA-256. Otherwise a correctly formed blob in a wrong/lookalike Git remote can satisfy the current readback language.

6. **The deletion coordinator does not fix where its authoritative intent/progress journal lives or its commit boundaries.** The plan promises one canary SQLite authority but describes an atomically persisted/fsynced transaction journal without saying whether it is a table in that same database or a second filesystem authority. This is critical for crashes between intent persistence, quarantine moves, the SQLite state mutation, and receipt finalization—especially when account hard-delete removes the user and all matched `ReviewRun` rows. Specify that intent, per-artifact progress, operation kind, terminal outcome, and receipt linkage live in the same marked canary SQLite database (or explicitly justify a non-authoritative filesystem WAL), define the pre-move intent transaction and final authoritative transaction boundaries, and require startup reconciliation to finish before any new mutation. Tests must prove there is never a second DB/auth/storage authority and that close/delete cannot report success while an unresolved intent remains.

7. **CER repeatability is checked against an image digest but not the actual scoring CPU/runtime identity.** CPU Whisper/PyTorch results can vary across architecture, CPU instruction paths, and linked math runtime even with one image, one thread, and deterministic algorithms. The plan records CPU readback but does not require the paid scorer to match the preflight fixture environment or rerun the fixture on the actual scoring host before threshold decisions. Pin the permitted architecture/CPU-runtime fingerprint and require the three-process fixture immediately in the exact scoring environment used for all 36 final files; fail closed on a mismatch or non-identical hash. Record that fingerprint/result with each scoring batch so a value near raw CER `0.10` cannot be accepted under an unvalidated runtime.
