# NOT READY

1. **The two-endpoint execution path is not defined and conflicts with the singular clone resolver contract.** The fixed application resolver accepts one clone endpoint/digest/source/model identity, while the paid matrix requires an audited-v13 baseline endpoint and a contract-v3 candidate endpoint. The plan never states which of the 44 slots run through durable application jobs versus a direct harness, how an audited-v13 response is accepted without weakening the contract-v3 verifier, or how each baseline and candidate slot is immutably bound to the correct endpoint/template/image before dispatch. This also makes “every clone job” snapshot/settlement acceptance untestable for any harness-direct slots. Define separate, typed baseline and candidate runner configurations, their exact dispatch paths, response contracts, and per-slot identity assertions; the AI Studio smoke must be explicitly bound to the candidate configuration.

2. **`failed_unknown_submit` is incompatible with the one-in-flight and cost contracts unless it halts or is authoritatively drained.** A transport-unknown `/run` may have created a live, billable provider job, but the plan permanently closes the slot, releases/refunds the reservation, and does not say whether later slots may dispatch. Continuing can create two in-flight jobs and understate committed cost. Require the full conservative charge to remain committed for an unknown submission and either terminate the paid run immediately or prove the endpoint queue/running state is empty before any later dispatch. The choice and its exact ledger/settlement behavior must be fixed and crash-tested.

3. **The pre-final ablation gate is not deterministic.** “Pass the CER rule” has no ablation-specific rule: the only stated CER gate is 17/18 candidate final files. Likewise, watermark validation does not explicitly require control `detect_fraction <= 0.5` and treatment `> 0.5`. The three-repeat final design also does not predeclare whether repeat seeds are distinct; using one seed for all three repeats would create duplicated deterministic candidate outputs. Freeze all 44 slot parameters before payment, including an explicit seed per slot with the same seed across each baseline/candidate pair and distinct predeclared repeat seeds, and state exact per-file ablation CER and watermark pass/fail predicates.

4. **The blind lock does not cryptographically commit the reveal mapping.** The locked HMAC covers the canonical score sheet only. The encrypted reveal is authenticated, but a holder of the review key can replace it with a different valid ciphertext before reveal unless its digest/mapping commitment is fixed before review. The plan also does not define the reveal plaintext schema needed to prove all 18 `pairId`/side-to-arm/slot/audio-hash mappings. Commit the canonical 18-pair reveal manifest (or its ciphertext digest) at run creation and include that commitment in the lock record/HMAC; specify canonical serialization and verify the complete bijection at lock and reveal.

5. **Review closure and account-deletion handling are incomplete.** The declared route set has no authenticated/CAS `close` operation or specified operator command even though `revealed -> closed`, quarantine/delete, and a sanitized receipt are required. Separately, account hard-delete covers the `UserVoice` reference but does not say how owner-linked generated WAVs, encrypted reveal, and raw scores in the private review store are found and recoverably removed if deletion occurs before Mew separately closes the evaluation. Define an idempotent, crash-recoverable close interface and include the review store in account hard-delete/reconciliation tests.

6. **The reference-deletion transaction has an uncovered crash window.** It moves opaque files into quarantine before durably writing/fsyncing the receipt, yet requires tests to crash after each move. A crash after the move but before the receipt can leave bytes that reconciliation cannot discover or associate. Persist and fsync an intent/receipt before the first move, or define a deterministic quarantine index/naming scheme that can recover receiptless moves; then state and test the invariant at every boundary for both single-voice and account deletion.

7. **The retention promise overclaims control of provider copies.** The fixed provider section correctly says `/status` disappearance is not proof of deletion from RunPod logs, backups, performance records, or legal holds, but Global Constraints and Acceptance Criteria say generated/review artifacts persist only until Mew closes the evaluation. Scope that promise explicitly to application-controlled review artifacts. The close receipt and final report must separately record the provider retention/deletion disposition established by the written RunPod gate and must not claim provider erasure unless independently evidenced.
