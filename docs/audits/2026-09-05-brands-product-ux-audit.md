# Audit `/brands`: ความน่าเชื่อถือของตัวอย่าง → สร้างคลิปสำเร็จ → กลับมาใช้ซ้ำ

วันที่: 2026-09-05 · Source HEAD: `20f1bd08` · ประเภทงาน: audit และข้อเสนอพัฒนา ยังไม่แก้ production

## ข้อสรุปสำหรับมิว

หน้าแบรนด์มีโครงสร้างบันทึกและนำสไตล์กลับมาใช้แล้ว แต่ตัวอย่างที่ใช้ตัดสินใจยังสื่อผลลัพธ์จริงได้ไม่ดี และหลังบันทึกยังไม่พาผู้ใช้ไปสร้างผลงานต่ออย่างชัดเจน การเปลี่ยนภาพการ์ดให้สวยอย่างเดียวจึงแก้ได้เพียงส่วนหนึ่ง

เป้าหมายของหน้านี้ควรเป็น **ผู้ใช้เลือกสไตล์ที่เข้าใจผลลัพธ์ นำไปสร้างคลิปที่ยอมใช้จริง และกลับมาสร้างซ้ำได้ง่าย** การสร้างแบรนด์หรือทดลองภาพเป็นขั้นระหว่างทาง ไม่ใช่ความสำเร็จปลายทาง

## ขอบเขตและความมั่นใจ

- ตรวจภาพที่มิวส่ง เทียบไฟล์ภาพจริงใน `public/style-packs/`, component, API, ตัวสร้างภาพการ์ด, preview, เส้นทางนำแบรนด์เข้า editor, telemetry และ North Star
- ตรวจประวัติ commit เพื่อแยกสิ่งที่ตั้งใจทำออกจากความผิดพลาดใหม่
- เปิด `https://studio.heroaiengine.com/brands` ผ่าน Browser แล้วถูกส่งไปหน้า login จึง **ยังไม่ได้ทดสอบ flow หลังล็อกอินบน production** หรือยืนยันว่า deployed HEAD ตรงกับ checkout
- ไม่มีการสร้างภาพเสียเงิน ไม่มีการเขียนฐานข้อมูล production และไม่มีตัวเลข conversion/usage สดใน audit นี้
- ทดสอบความครบของ asset ด้วย active catalog จริง ได้ผล FAIL: 7 ชุดเปิดใช้ แต่ไม่มี `thai-history.jpg`
- ชุดทดสอบ npm ยังรันไม่ได้เพราะ checkout ไม่มี dependency `tsx`; ใช้ Node native TypeScript สำหรับ asset check ได้ ไม่ถือว่า full test suite ผ่าน
- รอบนี้เป็น product audit จึงหยุดที่หลักฐานและแผนแก้ ไม่ทำ paid generation, prompt bisection หรือ regression-to-green ของสกิล diagnosing-bugs และไม่สรุปว่าโมเดลใดทำภาพผิดโดยไม่มีการทดลอง
- Audit 2 ก.ย. เป็นบริบทในอดีต ตัวเลขของวันนั้นไม่ใช่ baseline ปัจจุบัน และส่วน F5 มีการแก้นิยามอัตรา preflight ในเอกสารเดิมแล้ว

## North Star ที่ใช้ตัดสินใจ

โค้ดปัจจุบัน `src/lib/subscription-north-star.server.ts:107–190` นิยาม MAPC เป็น **ลูกค้าจ่ายเงินจริงที่ยังมีสิทธิ์ และสร้างผลลัพธ์สำเร็จอย่างน้อยหนึ่งอย่างใน 30 วันที่ผ่านมา** รวมลูกค้าที่จ่ายรายปีล่วงหน้าแม้ไม่ได้ตัดเงินอัตโนมัติ และแยก `activeRecurringPayers` ต่างหาก

ผลลัพธ์ครอบคลุมวิดีโอ สคริปต์ และภาพที่เข้าเกณฑ์; page view, preview, งานล้มเหลว และ retry ไม่เข้า MAPC นิยามนี้กว้างกว่า ADR 0008 รุ่นเดิมที่เน้น recurring เท่านั้น จึงควรปรับเอกสารนิยามให้ตรงกันก่อนทำ dashboard เพิ่ม

สำหรับ `/brands` ให้ optimize เส้นทาง **เลือกสไตล์ → คลิปแรกที่ใช้ได้ → คลิปถัดไป → paid activity / renewal** และติดตาม trial → recurring-paid แยกต่างหาก อย่าใช้จำนวนแบรนด์ที่บันทึกหรือจำนวนภาพทดลองเป็น North Star

## ตอนนี้ผู้ใช้ทำอะไรได้

1. เข้า “แบรนด์ของฉัน” เลือกแบรนด์เดิม สร้างใหม่ หรือใช้ค่าที่มีอยู่แล้ว หน้าเปิดให้ทุกแผนตามสิทธิ์คลังและจำนวนแบรนด์ที่รองรับ; gate ภาพ AI แยกออกไปแล้ว
2. ตั้งชื่อ เลือก 7 ชุดสไตล์ หรือ “กำหนดเอง” ซึ่งเปิดการตั้งค่าเพิ่มเติม ชื่อแบรนด์ไม่ได้เป็นคำสั่งสร้างภาพ เช่น “Mew Comic” ไม่ได้เลือกแนวการ์ตูนให้เอง
3. การเลือกชุดสไตล์เติมแนวภาพ ล็อกแนวเล่าเรื่อง สี บุคลิก ซับ และโทนบทบางส่วน โดยเก็บซับที่ผู้ใช้บันทึกเองและโทนที่ผู้ใช้เขียนเองตามกติกา มี mood ฟุตเทจ จังหวะและเพลงสำหรับ downstream
4. ผู้ใช้ที่มีสิทธิ์ภาพ AI ทดลอง 3 ภาพได้ โดยแจ้งสิทธิ์/เครดิตก่อนกด และอาจนำภาพเดิมกลับมาใช้เมื่อมีบริบทจากคลิป ทดลองไม่ใช่เงื่อนไขบังคับของการบันทึก
5. แบรนด์ใหม่กด “บันทึกเข้าคลังแบรนด์”; แบรนด์เดิมมี “บันทึกร่าง” กับ “ใช้แนวภาพใหม่นี้” เพื่อสร้าง revision ใหม่
6. นำแบรนด์ไปเลือกใน editor ได้ คลิปเดิมยึด revision เดิม; การแก้แบรนด์ไม่สร้างภาพเดิมใหม่อัตโนมัติ เส้นทางบันทึกจากคลิปมีอยู่แล้ว

หลักฐาน: `brands/layout.tsx`, `BrandLibraryClient.tsx:400–635,760–1001`, `style-pack-apply.ts:51–99`, `BrandVisualSelector.tsx` ภายใต้ `src/app/(dashboard)/video-editor/_v2/`

## Findings และความสำคัญ

### B01 — P1: ตัวอย่างบนการ์ดยังไม่เป็นหลักฐานของชุดสไตล์จริง

**ยืนยันจากโค้ดและไฟล์ภาพ:** API ส่งภาพ static `/style-packs/<id>.jpg` ตัวสร้างการ์ดใช้ Visual Format และ Treatment แต่ส่ง `brandVisualLanguage: null` ขณะที่การเลือกชุดสไตล์จริงเติม palette/personality และเส้นทาง preview ใช้ข้อมูลเหล่านั้น

ภาพธุรกิจ-การเงินจริงเป็นรูปโต๊ะกับคนสีเทาบนพื้นเบจ ส่วน catalog ระบุน้ำเงินเข้ม/น้ำเงิน/ขาว ภาพสุขภาพเป็นภาพวัตถุขนาดเล็กและมีพื้นที่ว่างมาก เมื่อย่อเป็นการ์ด ผู้ใช้มองเห็นสีพื้นมากกว่าลักษณะงาน ไม่มีตัวอย่างซับ เพลง จังหวะ หรือหลายฉากที่ชุดสไตล์ควบคุมด้วย

ความต่างของ prompt เป็นข้อเท็จจริง แต่ยังไม่อ้างว่าเป็นสาเหตุเดียวของคุณภาพภาพทุกใบ

**แก้:** ให้การ์ดและ demo มาจาก recipe เดียวกับการสร้างงานจริง บันทึก pack version, recipe version และ identity hash ของชุดสี/บุคลิก; ใช้ภาพหลายฉากหรือคลิปตัวอย่างสั้นที่อ่านสไตล์ได้ในขนาดจริง ผ่านการตรวจด้วยคนก่อนปล่อย ภาพตัวอย่างของ stock ต้องเป็นตัวอย่าง stock และภาพ AI ต้องระบุให้เข้าใจ

หลักฐาน: `scripts/generate-style-pack-cards.ts:134–143`; `src/lib/style-pack-catalog.ts`; `src/lib/style-pack-apply.ts:51–88`; `src/lib/brand-look-preview.server.ts:136–146`; `src/app/api/brand-library/route.ts:146`

### B02 — P1: การ์ดประวัติศาสตร์เป็น fallback ที่ตั้งใจทิ้งไว้ แต่หน้าตาดูเหมือนภาพตัวอย่าง

**ยืนยันด้วย asset check และประวัติ:** มี 7 active packs แต่ส่งภาพ 6 ใบ Commit `fa2eeda3` ลบภาพประวัติศาสตร์หลังภาพไม่ผ่านเกณฑ์ที่กำหนดไว้ ไม่ใช่หลักฐานว่า image API ล่มตอนมิวเปิดหน้า

`StylePackPicker` ซ่อน `<img>` เมื่อโหลดไม่สำเร็จ แล้วเปลี่ยนพื้นเป็น gradient โดยไม่มีข้อความอธิบาย จึงดูเหมือนระบบเจนภาพว่าง ๆ ทั้งที่ยังไม่มีตัวอย่างพร้อมใช้

**แก้:** ทำสถานะ sample เป็นข้อมูลชัดเจน เช่น ready/unavailable พร้อมข้อความ “ภาพตัวอย่างยังไม่พร้อม”; ยังเลือกชุดสไตล์ได้ถ้า recipe ใช้ได้ ไม่ควรปิดฟีเจอร์ที่ใช้งานได้เพียงเพราะ asset ขาด เมื่อได้ภาพที่ผ่าน review แล้วจึงเปลี่ยนเป็น ready เพิ่ม build check ว่า sample ที่ประกาศ ready โหลดได้และเป็นภาพจริง

หลักฐาน: `StylePackPicker.tsx:68–86`; commit `fa2eeda3`; ผลตรวจด้านท้าย

### B03 — P1: เปลี่ยนสไตล์แล้วภาพทดลองเดิมยังอยู่

**พบจาก state flow; ต้องยืนยันด้วย interaction test:** `selectStylePack` เปลี่ยน draft แต่ไม่ล้างหรือทำเครื่องหมาย preview ว่าเก่า `updateVisual` เช่นเดียวกัน ส่วน `BrandLookPreviewPanel` แสดง preview เดิมโดยไม่เทียบ identity ของ payload

ตัวอย่าง: ทดลองหนังผี → เปลี่ยนเป็นสุขภาพ → ภาพเดิมยังแสดงเป็น “ภาพทดลองแนวประจำแบรนด์” เสี่ยงให้ผู้ใช้ตัดสินใจและบันทึกจากหลักฐานคนละชุด

**แก้:** ผูก preview กับ hash ของ visual inputs ที่ใช้สร้าง เมื่อเปลี่ยนค่าที่ส่งผลต่อภาพให้แสดง “ตัวอย่างจากสไตล์ก่อนหน้า” พร้อมปุ่มทดลองค่าปัจจุบัน เก็บภาพเดิมไว้เพื่อเปรียบเทียบได้ การเปลี่ยนชื่ออย่างเดียวไม่ควรทำให้ต้องเสียเครดิตใหม่

Acceptance: A preview → เลือก B ต้องเห็น stale state ทันที; กลับ A แล้วจับคู่ snapshot ได้; stale state ไม่เรียกสร้างภาพเอง

หลักฐาน: `BrandLibraryClient.tsx:139,474–503,925–934`; `BrandLookPreviewPanel.tsx:138` เป็นต้นไป

### B04 — P1: ทดลอง 3 ภาพเป็นฉากทดสอบมาตรฐาน แต่ UI ทำให้คาดหวังตัวอย่างคอนเทนต์ของตน

**ยืนยันจากโค้ด:** เมื่อไม่มี source project ใช้ฉากพายุ, มือจัดวัตถุ 3 ชิ้น, และใบหน้าคน ชื่อ phase ถูกนำเสนอเป็นฉากเปิด/อธิบาย/ปิด แต่ไม่ได้เป็นเรื่องต่อเนื่องจากบทของผู้ใช้ `niche` มีผลเพียง content domain ไม่ได้เปลี่ยน subject เป็นเรื่องนั้น

### B05 — P1: บันทึกแล้วขาดทางไปสร้างผลงานที่ต่อเนื่อง

**ยืนยันจาก handler:** สร้างแบรนด์ปกติสำเร็จแล้ว reload ข้อมูลและแสดง notice ไม่มี CTA ที่ส่งแบรนด์ revision นี้ไปสร้างคลิปทันที เส้นทางจากคลิปมีการ pin ให้แล้ว แต่ยังควรมีปุ่มกลับคลิปต้นทางที่ชัดเจน

**แก้:** CTA หลัก “บันทึกและสร้างคลิป” ซึ่งบันทึกและส่ง revision ที่ได้ไปยังเส้นทางสร้างงานที่เหมาะสม; CTA รอง “บันทึกไว้ก่อน” ถ้ามาจาก editor ให้ “บันทึกและกลับคลิปนี้” ต้องไม่เรียก paid render จนผ่านการตัดสินใจตาม flow เดิม

Acceptance: สร้าง/เลือกแบรนด์ → เข้า editor โดยแบรนด์ถูกเลือกแล้ว ไม่ต้องค้นชื่อซ้ำ; ไม่สร้างโปรเจกต์ซ้ำเมื่อคลิกซ้ำ; refresh ยังคง revision ที่เลือก

หลักฐาน: `BrandLibraryClient.tsx:579–628,963–1001`

### B06 — P2: ผู้ใช้ต้องเลือกจากหมวดเนื้อหา แต่ตัวตนช่องและรูปแบบภาพเป็นคนละสิ่ง

**ประเมิน UX จาก UI/catalog:** ตัวเลือกแรกคือหนังผี ประวัติศาสตร์ การเงิน ฯลฯ แต่ผู้ใช้ที่ต้องการ “ช่องการ์ตูน” ต้องเข้า “กำหนดเอง” จึงจะเห็นแนวภาพ เช่น dramatic-comic การตั้งชื่อ Mew Comic ไม่ได้ช่วยเลือก และไม่มีบอกค่าที่ใช้อยู่ชัด ๆ บนการ์ด

นี่เป็นข้อแลกเปลี่ยนของ ADR 0058 ที่ทำให้เลือกง่ายด้วยชุดสไตล์ ไม่ใช่บั๊กว่าขาดระบบการ์ตูน จึงไม่ควรเพิ่มอีกหลายสิบชุดโดยยังไม่ทดสอบว่าคนเข้าใจต่างกันอย่างไร

**แก้:** ให้ชุดเริ่มต้นเดิมเป็นทางลัด แต่มีทางเข้าที่อ่านออก เช่น “อยากได้ภาพการ์ตูน/ภาพสมจริง/ภาพอธิบาย” และสรุปค่าที่เลือกให้เห็น การปรับ taxonomy หลักต้องปรับ ADR/CONTEXT ให้สอดคล้องกันหลังตัดสินใจ

แยกสิ่งที่จำแบรนด์ (ชื่อ เสียง สี ซับ โลโก้) ออกจากการเล่าเรื่องรายคลิปในความเข้าใจของผู้ใช้ โดยเก็บ default ที่เหมาะสมไว้เบื้องหลัง

### B07 — P2: คำอธิบายและรายละเอียดก่อนบันทึกยังไม่บอกผลที่จะเกิดครบ

**ยืนยันจาก UI:** “ทุกคลิปของแบรนด์นี้จะใช้สไตล์เดียวกัน เปลี่ยนทีหลังได้” อยู่ใกล้การ์ด แต่ข้อเท็จจริงคือคลิปเดิมยึด revision เดิม และ stock คุม mood ผ่านการค้น/จัดอันดับ ไม่ได้เปลี่ยนสีและลายเส้นให้ตรง AI ทุกเฟรม

เสียง ซับ โลโก้ซ่อนใน “ตั้งค่าเพิ่มเติม” ทั้งหมด ไม่มี summary บนหน้าหลักว่าปัจจุบันใช้ค่าอะไร Voice section ยังขอ provider และ voice ID ซึ่งเป็นภาระสำหรับผู้ใช้ทั่วไป

## Flow เป้าหมาย

ผู้ใช้ใหม่: **เลือกตัวอย่างฟรี → ตั้งชื่อ → เห็นสรุปภาพ/ซับ/เสียง → บันทึกและสร้างคลิป → export → ชวนใช้แบรนด์เดิมกับคลิปถัดไป**

ผู้ใช้กลับมา: **เลือกแบรนด์ → สร้างคลิปใหม่** โดยมีการแก้แบรนด์เป็นเส้นทางรอง

ผู้ใช้ที่อยู่ใน editor: **ลองสไตล์กับคลิปนี้ → เห็นผลที่ใช้ได้ → บันทึกเป็นแบรนด์ → กลับคลิปเดิม** ควรใช้ความสามารถ promote-from-project ที่มีอยู่ให้ครบก่อนสร้างระบบใหม่

ไม่บังคับสร้างแบรนด์ก่อนทำคลิปแรก และไม่บังคับซื้อ/ทดลองภาพก่อนบันทึก เพราะเพิ่มงานก่อนผู้ใช้ได้ผลลัพธ์

## แผนวัดผลที่สัมพันธ์กับ North Star

มี event สร้างแบรนด์, บันทึก, preview และ style_pack_selected อยู่แล้ว โดย selected บางเส้นทางนับเมื่อ publish ไม่ใช่เมื่อแตะการ์ด จึงใช้เป็น denominator ของการดู/ลองเลือกทั้งหมดไม่ได้

| Metric | นิยามเสนอ |
|---|---|
| Brand-assisted first export 24h | ผู้ใช้ใหม่ที่เริ่ม flow แบรนด์แล้วมี export สำเร็จจากโปรเจกต์ที่ pin revision นั้นภายใน 24 ชม. / ผู้ใช้ใหม่ที่เริ่ม flow และครบหน้าต่างสังเกต 24 ชม. |
| Time to first export | median และ p75 จากเริ่ม flow ถึง export แรก รายงานควบคู่ completion rate เพื่อไม่มองเฉพาะคนที่สำเร็จ |
| Repeat creation 7d | ผู้ใช้ที่มีคลิปสำเร็จแรกพร้อมแบรนด์ แล้วสร้างอีกโปรเจกต์สำเร็จใน 7 วัน / ผู้ใช้กลุ่มแรกที่ครบหน้าต่างสังเกต 7 วัน ไม่นับ rerender โปรเจกต์เดิมเป็นคลิปถัดไป |
| Repair burden | scene replacement/reroll ต่อ successful export แยก stock/AI และแยก technical retry ออกจาก creative repair |
| Paid outcome | trial → recurring-paid ตามหน้าต่าง conversion เดียวกัน และ MAPC ตามนิยาม server ปัจจุบัน; การเพิ่ม preview ไม่เพิ่ม numerator |

เชื่อม event ด้วย user, project, profile revision, pack/version, source และ cohort; เก็บเหตุการณ์จริงจาก server สำหรับ publish/pin/export ไม่ส่ง script หรือ prompt ส่วนตัวเข้า analytics โดยไม่จำเป็น

เพิ่ม client events สำหรับหน้าเริ่ม flow, sample viewed/failed, draft pack changed และ CTA ไป editor แยกจาก server event ที่ยืนยันการบันทึกแล้ว

แบ่ง new/returning, trial/paid, stock/AI และ internal/customer ให้ชัด มี baseline ก่อนเปลี่ยน UX เปรียบเทียบกลุ่มที่มีคุณสมบัติเหมือนกันหรือ experiment cohort เดียวกัน อย่าสรุปจากผู้ใช้ที่ตั้งใจสร้างแบรนด์เทียบกับคนอื่นว่าฟีเจอร์เป็นเหตุให้ retention สูงขึ้น

**Product targets ที่เสนอให้ทดสอบ ยังไม่ใช่ผลที่วัดแล้ว:** ผู้ใช้ทดสอบอย่างน้อย 4 ใน 5 คนเลือกสไตล์และเข้า editor พร้อมแบรนด์ได้โดยไม่ต้องอธิบาย, median ตั้งค่าก่อนเข้า editor ไม่เกิน 60 วินาที; ตัดสินการปล่อยจาก export/repeat creation ที่ดีขึ้นโดยต้นทุนต่อผลงานและ failure rate ไม่แย่ลง ใช้ขนาดตัวอย่างที่พอก่อนอ้างผล conversion

## การตรวจรับก่อนปล่อย

- ทุก sample ที่ ready โหลดสำเร็จ; unavailable มีข้อความ; review ภาพและ demo บนขนาดการ์ดจริงและมือถือ
- Preview A → เปลี่ยนเป็น B แสดง stale; เปลี่ยนชื่ออย่างเดียวไม่เสียภาพ; reroll ไม่ถูกเข้าใจว่าใช้ draft ใหม่เมื่อยังผูก snapshot เก่า
- เลือกชุดสไตล์ → summary → บันทึก → editor ได้ revision และค่าที่ตรงกัน รวมกรณีซับ/โทนที่ผู้ใช้กำหนดเอง
- คลิปเดิมไม่เปลี่ยนเมื่อ publish revision ใหม่; กลับจากโปรเจกต์แล้วไม่สร้างงานซ้ำ
- FREE/Trial/Paid เห็นความสามารถและราคาตรงกับ action; บันทึกได้แม้ไม่สร้างภาพ
- สลับแบรนด์/ย้อนกลับ/refresh ไม่ทิ้งร่างโดยไม่แจ้ง; keyboard ใช้ picker ได้และ focus เห็นชัด
- ราคา preview/reuse ตรง server; งานล้มเหลว/partial/recovery ไม่ทำให้ charge หรือสร้างงานซ้ำ
- มี browser tests ของ state transition จริงเพิ่มเติมจาก layout harness เดิม ซึ่งเน้น overflow/columns ไม่ใช่ความหมายของตัวอย่าง

## คำสั่งตรวจที่รันแล้ว

รันจาก repo root ด้วย Node 26 native TypeScript; อ่าน active catalog จริงและตรวจ asset path ที่ API ใช้ ไม่เรียก network:

```bash
node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --experimental-strip-types --input-type=module -e 'import assert from "node:assert/strict"; import {existsSync} from "node:fs"; import {activeStylePacks} from "./src/lib/style-pack-catalog.ts"; const packs=activeStylePacks(); const missing=packs.filter(p=>!existsSync("public/style-packs/"+p.id+".jpg")).map(p=>p.id); console.log(JSON.stringify({active:packs.length,missing,pass:!missing.length})); assert.deepEqual(missing,[],"Every active card needs a real sample image");'
```

ผล: `{"active":7,"missing":["thai-history"],"pass":false}` — exit 1

นี่เป็น red-capable asset check ของอาการการ์ดสีล้วน ไม่ใช่ข้อพิสูจน์ว่าทั้ง generation pipeline พัง และไม่ใช่การทดสอบคุณภาพภาพด้วย machine assertion หลังเพิ่ม sample state ควรเปลี่ยน contract ให้ตรวจทุกภาพที่ประกาศ ready แทนการบังคับให้ทุก active pack ต้องมีภาพ
